# 补充调研：系统磁盘清理应用与「边界」对照

**目的**：为 `disk-steward` 的 **SystemDomain** 补参考样本，重点不是"还能清什么"，而是**成熟工具在哪些地方集体收手**——边界是从别人的禁区里读出来的，不是自己拍出来的。
**数据时点**：2026-11-04。计数走 GitHub Search API `total_count`；规则库统计是对 `Winapp2.ini` 原文（1,829,579 字节）本地解析得出。

## 3. 规则库格式对照：五种先例，一个收敛结论

### 3.1 Winapp2.ini 实测结构（1.83 MB 原文解析）

```
[Google Chrome Caches *]                                   ← 节名 + * 标记
LangSecRef=3029                                            ← 分类
DetectFile=%LocalAppData%\Google\Chrome*                   ← 前置存在性检测
FileKey1=%LocalAppData%\Google\Chrome*\User Data|*-journal|RECURSE
FileKey2=...\User Data|Module Info Cache
FileKey5=...\*\*Cache*|*|REMOVESELF                        ← 删完自身
ExcludeKey1=PATH|%LocalAppData%\Amazon\Kindle\Cache\plugins\*\|*.db   ← 规则内排除
```

实测统计（本轮计算）：

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| 条目（节）数 | **4068** | 一个成熟清理规则库的真实规模 |
| `FileKey` 总行数 | **14121** | 平均每条例目 3.5 个文件目标 |
| `RegKey` 总行数 | **3677** | 注册表目标仍有相当比重（我们不打算做，见 §5） |
| `DetectFile` 总行数 | **3322** | **81.7% 的条目带前置存在性检测**——先确认软件装了，才给目标 |
| `ExcludeKey` 总行数 | **86** | 少量但关键：**排除项写在规则内部**（例：Kindle 缓存里的 `*.db` 不删） |
| `Warning` 行 | **5** | 显式警告文本极少（见 §4.3） |
| 节名以 `*` 结尾 | **4068 / 4068（100%）** | `*` 已退化为格式约定，**不再承载"这是危险项"的信号** |
| `REMOVESELF` / `RECURSE` | 5528 / 2186 | 两种删除语义：删后自清空目录 / 递归 |

### 3.2 五种格式的字段能力对比

| 能力 | Winapp2.ini | CleanerML (BleachBit) | cleanmgr `/sageset` | gargantua YAML | **disk-steward rules.json（本设计）** |
| --- | --- | --- | --- | --- | --- |
| 目标路径 + 模式 | ✅ FileKey + 通配 | ✅ | ❌ 只有内置开关 | ✅ | ✅ `match` |
| 前置存在性检测 | ✅ `DetectFile` | ✅ | 内置 | ✅ | ⚠ **本轮新增 `detect`** |
| 规则内排除 | ✅ `ExcludeKey` | 部分 | ❌ | 未见 | ⚠ **本轮新增 `exclude`** |
| 删除语义（递归/自清） | ✅ `RECURSE`/`REMOVESELF` | ✅ | — | — | ⚠ **本轮新增 `flags`** |
| 分级（安全/谨慎/危险） | ⚠ 仅有 `*`（已失效） | 部分 | 按开关分组 | ✅ 安全规则 | ✅ `grade` 五值 |
| 判定理由（给人看） | ⚠ 仅 5 条 `Warning` | 部分 | ❌ | ✅ + 本地 AI 解释 | ✅ `reason` 必填 |
| 执行前置条件（先停服务/先启动一次） | ⚠ 混在 `Warning` 文本里 | ❌ | ❌ | 未见 | ⚠ **本轮新增 `precondition`** |

**收敛结论**：主流规则库都在解决同样的四件事——**在哪找（detect）、删什么（targets+flags）、不能删什么（exclude）、删之前要知道什么（warning/precondition）**。我们的 `rules.json` 第一版只有 `match/grade/reason/executor`，缺了前三件中的三件。这是本轮调研最直接的产出。

## 4. 边界三层：从别人的禁区读出我们该守什么

### 4.1 共识禁区（成熟工具集体不碰，或只在显式警告下碰）

| 目标 | 为什么所有成熟规则库都避让 |
| --- | --- |
| 浏览器凭据库本体（`Login Data`、`key4.db`、`Cookies` 的密钥部分） | 删了等于注销所有账号；CCleaner 历史上因此出过事故 |
| 正在被占用的数据库文件（`*.db` / `*-journal` / `LOCK`） | 删除后应用可能损坏数据；Winapp2 用 `ExcludeKey` 明确排除 `*.db` |
| `Program Files`、`Windows\System32` | 无条件禁区；清理工具的收益为零、破坏面最大 |
| `WinSxS` 本体（非 DISM 路径） | 硬链接共享，直接删会破坏组件存储（主报告 §5.5） |
| `pagefile.sys` / `hiberfil.sys` | 影响稳定性与休眠；系统提供专门开关，不需要第三方删 |
| 卷影副本 / 还原点 | 是改配置类操作唯一的退路（主报告 §8.2） |
| 凭据管理器 / DPAPI 密钥 / 浏览器 cookie 加密密钥 | 删除等于丢失全部登录态 |
| 用户文档目录（`Documents`/`Desktop`/`Pictures`） | 即便"看起来是缓存"，也不属于清理范畴 |

### 4.2 分歧区（有的清、有的不清 → 我们一律不自动清，只进"谨慎"级）

| 目标 | 分歧点 | 我们的处理 |
| --- | --- | --- |
| 浏览器"会话恢复"文件（Session/Current Tabs） | 清了会丢标签页，很多人当缓存 | 🟡 谨慎，逐项确认 |
| 缩略图/图标缓存 | 重建有代价（大图库可达数分钟） | 🟡 |
| `Windows.old` | 省几 GB，但失去回滚上一版本系统的能力 | 🟠 建议迁移/由用户手动，**不自动** |
| Prefetch | 有研究认为 SSD 上收益低，但删除会短期拖慢启动 | 🟡 |
| 字体缓存 | 删了首次显示会卡 | 🟡 |
| Store/UWP 应用缓存 | 应用私有格式，无法判断 | 🔴 保护（除非规则明确 `DetectFile` + 官方文档） |
| 包管理器缓存（npm/pip/cargo/go） | 重建需联网下载（kondo 类工具专做此事） | 🟠 建议迁移 store 路径，而非删除 |
| 项目构建产物（`node_modules`/`target`/`.venv`） | 可重建但可能离线失败 | 🟡（实测：天枢 `plugins/media-toolkit/node_modules` 61.5 MB 即此类） |

### 4.3 `Warning` 信号为什么会失效（一条可直接借用的教训）

实测：4,068 条规则里只有 **5 条** 写了 `Warning`，而节名末尾的 `*` 出现在 **100%** 的条目上。也就是说，**曾经用来标记"危险项"的 `*` 已经变成纯格式约定，警告信息退化成了 5 条自由文本**。这 5 条文本恰好覆盖四类真实风险：

| 原文（节选） | 风险类型 |
| --- | --- |
| "This will also delete all app-specific settings." | **副作用**：删缓存连带删设置 |
| "This will cause you to redownload the Paramount Dynamic RSS file." | **可恢复但需重下** |
| "…only be enabled after you have launched each of your installed Steam games at least once. Deleting these files before then may cause Steam to think the game's installation is broken." | **执行前置条件**（状态依赖） |
| "You need to run this in Windows Safe Mode. Or stop services … prior to cleaning and restart after cleaning." | **环境前置条件**（必须先停服务） |

对我们直接可用的结论有两条：

1. **不要用"标记"承载语义**（`*` 的教训）——语义要结构化：`grade`（多严重）、`precondition`（先决条件）、`sideEffect`（副作用）是三个不同的维度，混在一个字段里必然退化。
2. **前置条件是独立维度，不是分级**：Steam 那条不是"危险"，而是"顺序错了就出事"。这类规则必须能被机器检查（例如 `precondition: {kind: "fileExists", path: "…/steamapps/appmanifest_*.acf"}`），而不是靠人读警告。

## 5. 落到 `disk-steward` 的 7 条修订

| # | 修订 | 依据 |
| --- | --- | --- |
| 1 | `rules.json` 增加 `detect`（前置存在性，glob）——**无 detect 命中的规则不参与扫描** | Winapp2 3,322 条 `DetectFile`，占条目 81.7% |
| 2 | 增加 `exclude`（规则内排除，优先级高于 `match`） | Winapp2 `ExcludeKey` 原文：`ExcludeKey1=PATH|%LocalAppData%\Amazon\Kindle\Cache\plugins\*\|*.db`（路径段与文件段用 `\|` 分隔） |
| 3 | 增加 `flags`：`recurse` / `removeSelf` | Winapp2 `RECURSE` 2,186 / `REMOVESELF` 5,528 |
| 4 | 增加 `precondition`（机器可检查的执行前置）与 `sideEffect`（人读的副作用），且**不参与分级** | Winapp2 5 条 `Warning` 的四类风险 + `*` 信号失效的教训 |
| 5 | SystemDomain **首批只覆盖共识目标**（`%TEMP%`、`%LOCALAPPDATA%\Temp`、缩略图缓存、`WinSxS` 走 DISM、`Windows Update` 下载缓存、回收站），分歧区目标一律不进默认规则库 | §4.1 / §4.2 |
| 6 | 不做 `RegKey` 类目标（Winapp2 有 3,677 条，我们全放弃），并在 `disk_rules` 里能解释"为什么不支持" | 主报告 §8.3（注册表清理收益不可测、误删不可逆） |
| 7 | ts 域新增"项目可重建物"规则族（`node_modules`/`target`/`.venv`/`__pycache__`），执行器只允许 `stage` + 记台账，默认不 `purge` | kondo（依赖与构建产物清理）+ 本机实测 `media-toolkit/node_modules` 61.5 MB |

## 6. 未核实项

- **CleanerML 的具体字段集**：本轮只核到其定位（"System cleaners written in CleanerML"），未逐字段读 XML 定义。
- **`gargantua` 的 YAML 规则字段**：仓库描述提到 "YAML-driven safety rules"，未读其规则文件，字段能力见 §3.2 一栏标注为"未见"。
- **`cleanmgr /sageset` 的开关编号全集**：属 Windows 内置行为，本轮未在真机枚举（不影响设计：我们不封装 `cleanmgr`）。
- **kondo 的判定清单**：未读其规则表，"哪些目录算可重建"目前依据仓库描述与本机实测两处，非全量。
- **`Warning` 之外的隐式风险**：Winapp2 只有 5 条显式警告，其余 4,063 条的风险只能从 `FileKey` 目标逐条推断，本轮未做全量审计（也不建议做，成本高于收益）。
