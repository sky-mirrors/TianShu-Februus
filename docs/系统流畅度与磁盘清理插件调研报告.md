## 1. 方法学与口径（为什么这些数可信，以及它们不能证明什么）

### 1.1 DSH 侧怎么数的

DSH 的插件目录是一份 format-1 索引 JSON，发布在 npm 上（`dsh-plugin-catalog`），由 `awesome-dsh-plugin.com` 维护，插件市场的「发现 → 索引源」与 `plugin_market` 智能体工具消费的是同一份文档。我把整份索引（3.6 MB）拉下来本地解析，得到 4481 条 plugin 记录，字段为 `name / title / description / homepage / repository / metadata / versions`，`metadata.category` 是枚举值，共 23 类。

统计规则固定如下，任何人可复算：

- **分类分布**：按 `metadata.category` 直接计数，不猜。
- **关键词命中**：把 `title` + `description`（中英双语字段拼起来）转小写后做子串匹配，一词命中即计。这是**召回优先**的规则，必然带假阳性——所以每个结论都追加人工复核。
- **磁盘清理 A 组**：命中集合 {磁盘, disk, c盘, c drive, 空间, space, junk, 垃圾, 残留, leftover, cache, 缓存, 回收站, trash} 且命中集合 {清理, clean, purge, delete, 释放, 删除, 迁移, migrat, quarantine, 回收, sweep, wipe}。结果 97 条，逐条看标题后只有 3 条是系统级磁盘清理（其余是"清理上下文缓存""删除会话""清理插件残留"等）。
- **性能 B 组**：命中 {性能, perf, fps, 帧, 卡顿, 流畅, 延迟, latency, 加速, speed, 响应速度, smooth}。结果 105 条，人工复核后 6 条真正与"流畅度"相关（其余是"性能剖析 LLM 缓存""提示词优化"等语义漂移）。

注意一个**统计陷阱**：`dsh-prompt-optimizer`、`dsh-input-optimizer` 这类插件在中文描述里写的是"提示词优化"，"优化"两字会大量命中，和系统优化毫无关系。所以本报告里凡是"优化"类的计数，我都回到 README 语义确认，而不是相信关键词。

### 1.2 市场 8655 与目录 4481 的差额

差的这 4174 个不是丢失数据，是两个不同口径：市场站点的 8655 是**在架插件总数**（含未被精选收录、只有版本号没有中文描述、以及同一仓库的多个子包），目录索引的 4481 是**经过人工精选并给出中英双语描述**的条目。同一个仓库的多个子包在索引里会以 `owner/repo#subpath` 形式出现（例如 `zhu1090093659/dsh-web#packages/dsh-task-board`），所以两边不可能一一对齐。

**本报告的所有"比例"类结论都以 4481 为分母，并明确标注**；凡是引用 8655 的地方都只是复述站点口径。

### 1.3 GitHub 侧怎么数的

直接请求 GitHub Search API（`/search/repositories`）取 `total_count`，以及按 `sort=stars` 的前 5 名。这带来两个必须写明的限制：

- `total_count` 是**检索命中数，不是质量数**。`"system optimizer"` 命中 2259 个仓库，第一名是 `vercel/turborepo`（31304 stars）——它是个构建系统，"optimizer" 出现在描述里的别处。所以我把每组查询的 top5 也列出来当"噪声证据"，让读者自己看这个数字有多脏。
- 检索结果**动态变化**。本报告所有数字都是 2026-11-04 的快照，重跑会有漂移。

### 1.4 本报告不声称的事

- 不声称"某工具能让你的机器变快 X%"。绝大多数项目自己也没做过对照实验（唯一的量化自证出现在 `dsh-perf-boost` 的 README：200 Hz 显示器上空白页 187–200 fps、新会话 200 fps、2.3 万事件会话约 156 fps，p50 帧时 5.0→6.4 ms）。这类数据是**单机、单场景、开发者自测**，不能外推。
- 不声称某个清理规则"绝对安全"。所有清理工具的安全性都取决于规则库的覆盖面，而规则库永远追不上软件生态的变化。

## 2. 名词校准：先把两个被用坏了的词说清

### 2.1 "系统流畅度"到底是什么

用户说"卡"，实际可能落在五个完全不同的物理层，每一层对应的工具、代价、可改善空间都不一样：

| 层 | 物理量 | 卡的表现 | 可改善手段 | 改善上限 |
| --- | --- | --- | --- | --- |
| 渲染/合成 | 帧时（frame time）、掉帧 | 滚动发涩、动画一跳一跳 | 减少 DOM 体量、`content-visibility`、暂停合成器空转 | 受 GPU/显示器刷新率封顶 |
| 主线程 | Long Task（>50 ms）、LoAF | 点击后 200 ms 没反应 | 拆分长任务、让路、空闲批处理 | 受单核性能与 JS 引擎限制 |
| 内存 | 工作集、提交量、standby list | 切换应用卡、磁盘狂响 | 释放缓存、减少常驻、加内存 | 物理内存是硬边界 |
| 磁盘 IO | 队列深度、IOPS、4K 随机延迟 | 打开文件慢、开机慢 | 减少扫描、预热缓存、换 SSD | 介质决定 |
| 调度/中断 | DPC/ISR 延迟、优先级 | 音频爆音、输入延迟 | 中断亲和、MMCSS、电源计划 | 驱动与内核决定 |

市面上 90% 的"优化软件"只碰第 3、4 层（清内存、删文件），第 1、2 层（渲染与主线程）只有在**应用自身是瓶颈**时才有意义——这也是 DSH 生态里那批"渲染让路（yield）"型插件的位置，它们优化的不是 Windows，是 DSH 自己的前端。

### 2.2 "磁盘清理"的可删性谱系

按"删了之后能不能恢复、代价多大"，把候选目标排成一条谱系（从左到右越来越不可逆）：

```
纯缓存（可重建，秒级）
  → 可重建但代价高（IDE 索引：重建几小时；端侧 AI 模型：重新下载几 GB）
    → 迁移可解（包管理器缓存、虚拟磁盘：搬到别的盘，用 junction/配置指向）
      → 保护名单（用户文档、凭据、聊天记录、虚拟磁盘本体：删了就是事故）
        → 系统组件（WinSxS、组件存储、还原点：删了可能无法回滚或无法卸载更新）
```

这条谱系是本报告后面所有"边界"讨论的基准轴。判断一个清理工具好不好，先看**它的规则库有没有在这一维上分级**，而不是看它删得干不干净。

### 2.3 第三个被用坏的词："优化"

这个行业里"优化"至少被用在三种互斥的含义上，而它们**不可能同时成立**：

| 含义 | 做法 | 牺牲什么 | 样本 |
| --- | --- | --- | --- |
| 减少工作量（avoid work） | 不启动、不扫描、不渲染看不见的东西 | 功能即时性 | debloat 脚本、渲染让路 |
| 减少工作集（smaller footprint） | 释放缓存、trim 工作集、删文件 | 后续访问要重新付出代价 | memreduct、WinMemoryCleaner |
| 减少等待（lower latency） | 预读、缓存、提高优先级、降延迟 | 内存与带宽占用 | dsh-perf-boost 的大会话预热、PC-Optimization-Hub 类 |

看出来的矛盾是：**减少工作集与减少等待直接对撞**（缓存就是为了减少等待而占内存）；**减少工作量与减少等待也对撞**（不预读就没有冷启动优势）。所以任何声称"全面优化"的工具，实际都在替用户做一个未声明的取舍。

因此判断一个工具是否专业，只需三问：

1. **它优化的是谁**——进程、宿主、还是整个系统？报表里说"提升 40%"却不说是哪个指标提升，等于没说。
2. **代价由谁付**——速度是拿内存换的？还是拿空间换的？代价不写出来的优化工具，通常代价由用户在某天突然承担。
3. **基线是什么**——没有基线（同机、同负载、同会话规模的对照测量）的百分比就是广告。

本报告后面 §4.4 把 `dsh-perf-boost` 单独拎出来讲，就是因为它把这三问全答了：优化对象是渲染进程、代价逐项列出、基线给出实测帧率与帧时。

## 3. DSH 插件生态：架构先说清，再数数

### 3.1 一个 DSH 插件在物理上是什么

从 `dsh-windows-c-cleanup` 与 `dsh-workspace-cleaner` 的 README 可以还原出完整的装载链路，这比任何"插件市场"的宣传都更能说明它的能力边界：

```
用户执行 dsh plugin --profile <profile> add <spec>
        │
        ├── spec = 包名            → pnpm 从 npm 拉预构建产物（无编译、无审批）
        ├── spec = github:owner/repo → pnpm 拉 git 源，跑 prepare 脚本现场构建（需审批）
        └── spec = link:/绝对路径   → 以软链装进 profile（改代码立即生效）
        │
        ▼
pnpm 把包装进指定 profile 的 node_modules
        │
        ▼
按"装载后的真实状态"登记进 dsh.profile.bundles
        │
        ├── 声明了 dsh.bundle.patch 的包 → 进入层叠（bundle + patch row）列表
        └── 未声明的 → 只是普通依赖，不进层叠
        │
        ▼
宿主启动时按层叠顺序装配：
        Host 半（Node 侧）= 注册工具、注册 HTTP 接口、读文件系统、起子进程
        Client 半（浏览器侧）= 注册 UI 页签/浮层/侧栏、拦截渲染
        │
        ▼
生效语义：改了 Host 半 → 必须重启 dsh；只改 Client 半 → 刷新页面即可
卸载：dsh plugin --profile <profile> remove <name>
```

这段链路解释了四件在"数量统计"里看不到的事：

1. **插件的权限 = 宿主进程的权限**。Host 半跑在 DSH 的 Node 进程里，它拿到的文件系统与子进程能力，和你手动开一个终端是同一档；插件自己再调 PowerShell 提权，就摸到了管理员。`dsh-windows-c-cleanup` 明确写了它需要 UAC 提升来碰系统目录——这不是它越权，是它把宿主没有的能力**显式**要了过来。
2. **Client 半改不了操作系统**。`dsh-perf-boost` 明确写"全部改动只发生在渲染进程"，`dsh-perf-hud` 写"纯客户端"。这两个插件的"性能优化"对象是 DSH 前端，不是 Windows。把它们当系统加速器是误读。
3. **"装完即生效"分两档**。`dsh-pancha` 说"装完刷新页面，无需重启宿主"（纯 Client + 已有工具面），`deepclean-mydisk` 说"装完要重启 DSH"（有 Host 半）。用户侧的可感差异是：不需要重启的插件通常能力更窄。
4. **git 装法会引入构建**。`dsh-windows-c-cleanup` 的 `lib/` 与 `client/client.js` 是构建产物、不提交进仓库，所以从 git 装会触发 `prepare` 现场构建并需要审批；npm 装法带预构建、无审批。**同一份代码，两种装法的信任模型不一样**——这是供应链讨论的落点（见 §7）。

### 3.2 磁盘清理类：从 97 个候选到 3 个真货

按 §1.1 的 A 组规则筛出 97 条，全部看标题后，真正对**操作系统磁盘**动手的只有 3 个：

| 插件 | 作者 | 定位 | 关键机制（来自 README） |
| --- | --- | --- | --- |
| `dsh-windows-c-cleanup` | runcat-tommy | Windows 系统盘（C:）清理 | 扫描 → 五级分级 → 可视化报告 → 用户选择 → 分层执行/迁移 |
| `dsh-pancha`（盘查） | vlln | 跨平台磁盘审查盘面 | 树图 + Agent 写语义 + 用户做决定 + 预览后移入废纸篓 |
| `deepclean-mydisk` | huangxiaoliang | macOS/Windows 原生侧栏磁盘工具 | 只读扫描 + 两阶段清理（先隔离/废纸篓，二次确认才永久删） |

另有 7 个做 **DSH 自身的磁盘回收**（不是操作系统清理，但对重度用户是真实的空间来源）：

| 插件 | 回收对象 | 边界 |
| --- | --- | --- |
| `dsh-workspace-cleaner` | 工作区 + 对话 + 会话日志 + 投影缓存 + 登记 | 删除不可撤销；`~/.dsh` 下的记录/日志/缓存 |
| `dsh-brutal-delete` | 会话（单条 / 跨工作区批量） | "暴力"删除，从磁盘彻底抹掉 |
| `dsh-tool-session-delete` | 单会话及其日志文件 | 确认弹窗会报日志大小与实时活动状态 |
| `dsh-plugin-update-center` | 插件卸载残留 | 带快照、回滚、排队更新 |
| `dsh-batch-uninstall` | 批量卸载插件 | 设置页 checklist |
| `dsh-plugin-diraud` | 插件目录治理（分组/禁用/卸载） | 不打磁盘 |
| `dsh-unplug` | 干净拔插插件（含 patch row 清理） | 卸不干净是 DSH 插件生态的真实痛点 |

值得单独指出：`dsh-workspace-cleaner` 的存在本身就暴露了宿主的一个设计取舍——DSH 自带的"移除工作区"**只摘登记、不删数据**，会话会掉进"未分组"继续占盘。这类"半个功能"是第三方插件最稳定的需求来源。

### 3.3 流畅度类：从 105 个候选到 6 个真货

| 插件 | 作用层 | 机制（README 原文要点） | 边界 |
| --- | --- | --- | --- |
| `dsh-perf-boost` | 渲染进程 | `content-visibility: auto` 接管长列表子项、rAF/定时器接管、空闲降帧 30fps、媒体懒加载、后台暂停定时器/视频、会话列表节流、大会话预热（Host 侧只读预读文件缓存） | 全部渲染侧；提供"可能会导致"清单（空白一瞬、动画变慢、滚动回来看黑一下） |
| `dsh-perf-hud` | 渲染进程（观测） | 帧与最差帧、Long Task 四条腿归因（组件/包/DOM 写入者）、每插件回调速率与同步耗时、宿主 event-loop p50/p99、链路 RTT、证据包导出、守夜层（>100 ms 自动抓前 10 s 后 3 s） | 纯客户端；不采 Host CPU trace；导出前做减法脱敏 |
| `sidebar-perfmon` | 宿主/系统 | 右侧栏 CPU、内存、swap、GPU 频率与 VRAM、CPU/GPU/主板/硬盘温度 | 只观测不改；依赖传感器可读性 |
| `dsh-fast` | 宿主（LLM 链路） | 上下文工程、延迟剖析、缓存行为报告 | 优化的是 token/缓存，不是帧 |
| `kid-sysmon` | 系统 | 一张卡片看 CPU/内存/磁盘概况 | 只读摘要 |
| `dsh-web-network-optimizer` | 传输层 | 缓存与压缩减少传输体积、断连指示 | 只影响页面加载，不影响运行时帧率 |

这里有一个必须点明的**语义陷阱**：这 6 个里只有 1 个（`dsh-perf-boost`）真的在"让界面变流畅"，2 个是"让你看见为什么不流畅"（HUD/monitor），3 个是别的东西。也就是说，DSH 生态里"提升流畅度"的有效供给 = **1 个插件**。这个结论对选型很重要：想靠装插件把 DSH 变快，可选项其实只有一个，剩下的路是**减负**（关插件、缩会话、降特效）。

### 3.4 顺手摸到系统边界的三类插件

这三类不算"清理/加速"，但它们决定了 DSH 能不能安全地做系统级操作，是架构讨论的必要拼图：

- **`dsh-desktop-autostart`**：往 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup` 放一条快捷方式，走 `WScript.Shell` COM，**明确不写注册表、不建计划任务、不需要管理员**；并且"写后读回、删后确认，任何一步失败都会报错"。这是本报告见到的最小权限、最可核查的 Windows 集成实现——反面教材是大量"优化软件"用注册表 Run 键 + 后台服务 + 驱动三件套。
- **`dsh-ops`**：为 Windows 上的 DSH 提供 bash、PowerShell 7 与 Rust 高性能工具，目的是减少 token 消耗——即"用更少的输出换同样的信息"，这是"流畅"在 agent 语境下的另一种含义（不是帧率，是往返次数）。
- **`dsh-mcp-registry`**：MCP 连接器的治理注册表，四级 fail-closed 授权，拒绝畸形参数——插件生态里少见的安全原语。
- **`dsh-sandboxie-redirect`**：写时复制权限预设，shell 命令在 per-workspace 的 Sandboxie 盒子里跑，工作区外的写入落在盒子副本里，真机不受影响。这是把"Agent 会乱删"这个风险**从提示词软约束搬到操作系统硬约束**的唯一一个样本。

## 4. DSH 侧深描：三个清理插件，三种架构赌注

同一个需求（"把 C 盘腾出来"），三个插件选了三条不同的路。放在一起看，能看清"哪一层该由谁负责"这个真正的架构问题。

### 4.1 `dsh-windows-c-cleanup`：把清理做成一条可审计流水线

**它拒绝的前提**：README 开篇就否掉了主流做法——"它不是「一键删缓存」脚本"，而是"扫描 → 五级分级 → 生成可视化报告 → 用户选择 → 分层执行 / 迁移到其他盘"。

**它的核心洞察**（值得单独摘出来，因为这是本报告见到的最准确的一句话诊断）：

> C 盘爆满通常不是「垃圾文件」造成的，而是**本该放在别的盘的东西放错了地方**：包管理器缓存、IDE 索引、浏览器端侧 AI 模型、升级包残留、虚拟磁盘。

这句话把问题从"删"改写成"归位"。对应的工程后果是：`删除` 只是四类动作里的一类，另外三类是 `迁移`、`保护`、`长期防护`。

**五级分级（架构的核心）**：

| 级别 | 含义 | 执行策略 |
| --- | --- | --- |
| 🟢 可安全删除 | 缓存 / 临时文件 / 升级包残留，无数据损失 | 确认一次后可批量执行 |
| 🟡 谨慎删除 | 可重建但代价高（IDE 索引、端侧 AI 模型、包管理器仓库），或需管理员权限（WinSxS 走 DISM） | 逐项确认 |
| 🟠 建议迁移 | 搬到其他盘后应用无感，用 junction 或改配置 | 迁移 + 建链接 + 记台账，可回滚 |
| 🔴 保护名单 | 用户文档、凭据、聊天数据、虚拟磁盘、IDE 配置、未识别路径 | 永不自动删除（硬约束，用户规则也不得覆盖） |
| 🔵 长期防护 | 缓存重定向、存储感知、虚拟磁盘位置核查 | 一次性做好，长期少清理 |

**架构上真正起作用的三条设计**：

1. **"不明即不删"是硬约束，不是策略**。未收录规则的路径一律按保护处理，且这条约束**优先级高于用户自定义规则**——用户写了一条错规则也不会突破它。这是把 fail-closed 从口号落到规则引擎的默认值上。
2. **先量后删**。每个候选项都要测出真实大小并写进 Markdown 报告。这解决的不是安全问题，是**信任问题**：用户看到"IDE 索引 4.2 GB / 重建约 3 小时"这种描述，才可能做出正确决定。
3. **迁移优先于删除**，且迁移动作要记台账、可回滚。junction 把缓存目录搬到 D 盘后，应用无感，且**长期不再回涨**——这是唯一能改变"每月都要清一次"这个循环的动作。

**边界（它做不到的）**：

- 平台边界：Windows 专属，规则库按 Windows 路径写死，换 macOS 直接失效。
- 权限边界：碰系统目录要 UAC；不提权就只能清用户态缓存。
- 判定边界：五级分级依赖规则库的人工维护，新软件（尤其是新的端侧模型缓存路径）在没有规则前一律落进"保护"，**表现为漏清，而不是误删**——这是刻意的偏保守选择，代价是"清不干净"。
- 不可逆边界：WinSxS 走 DISM 清理后**无法卸载已安装更新**，这条 README 没有展开，但它是该系统级操作的内禀属性（见 §8）。

### 4.2 `dsh-pancha`（盘查）：把"执行权"从 Agent 手里拿走

**它解决的问题不是清理，是判断**：

> Finder 和 SpaceSniffer 只回答「哪个文件夹大」，不回答「它是什么、删了会怎样」。

**架构赌注：Agent 只写标记，不碰文件。** 这是本报告见到的、对"Agent 清理磁盘"这一命题最克制的一个答案：

- Agent 的工具面是 6 个**纯数据**工具：`disk_canvas_scan`（扫描直接子项）、`disk_canvas_state`（读盘面）、`disk_canvas_claim`（写一条语义：一句话 + 类别 + 依据）、`disk_canvas_mark`（标决定，只补没决定的）、`disk_canvas_object`（对不同意的决定写异议，不改决定）、`disk_canvas_history`（读历史）。
- **"它没有执行权，只能写标记"**——真正移动文件必须由人点「执行清理」。
- 用户决定优先于 Agent 语义："它只能写「异议」，不能改你的决定"。
- 执行动作只有一种：**移动到废纸篓**，没有删除接口；macOS 拒绝写废纸篓时退到 `$DSH_HOME/trash/<时间戳>/`，界面写明去向；成功记成一批，"撤销这批"可移回。
- 扫描只读 `readdir`/`stat`，**不跟随符号链接**（这一条防的是"扫穿整个磁盘"和"删到链接目标"两类事故）。

**它的边界，README 自己写清楚了，而且写得很诚实**：

> 约束来自投递消息里的提示词：**只分析、标注、预览，不直接改动文件**。这是软约束——默认会话本身仍有文件/命令工具；要工具级隔离，需要自己加一个受控 preset。

这句话是整个 DSH 生态最重要的一句自我披露：**"Agent 不会乱删"在同会话里是提示词承诺，不是权限事实**。同一个会话里 Agent 仍然握着文件工具与 shell。想让约束变成事实，得换执行环境（Sandboxie 盒子、只读挂载、单独的低权 profile）。

另有两处工程细节值得记下来：盘面数据落 `$DSH_HOME/data/dsh-pancha/ledger.json`（本机、不上传、无遥测）；只把扫描结果摘要发给模型。这是"本地账本 + 最小外发"的正确形状。

### 4.3 `deepclean-mydisk`：两阶段清理，把"释放空间"延迟到第二次确认

**它的一行定位**：扫描只读，清理只移动——先移入废纸篓（macOS）或隔离区（Windows），**永久删除必须二次确认，且只限本插件移入的批次**。

这个设计选择解决了一个非常具体的老问题：**"清理"与"释放"被混为一谈**。移到废纸篓并不释放空间（macOS 的废纸篓仍在同一卷上），所以很多用户的体验是"清完还是满的"。`deepclean-mydisk` 把这两步显式拆开，并在历史页显示"隔离区/废纸篓占用"与"永久删除"入口——**空间占用与删除动作同屏可见**，用户不会误判。

**架构要点**：

- 平台差异被摆到台面上：macOS 需要「完全磁盘访问」权限（TCC），未授权时**不做任何扫描**（设置页有"权限检查"）；Windows 没有对应概念，只报告当前是管理员还是普通用户。
- 扫描器实现：macOS 用系统自带 `python3` + `du`/`plutil`/`sips`；Windows 用 `py -3`，扫描与照片解码为纯 Python + PowerShell `.NET`，**不依赖 Pillow**。这是一条"尽量少装依赖"的工程纪律。
- 结果分四档：推荐清理 / 可选清理 / 需确认 / 受保护；7 个内容分类（开发缓存、浏览器缓存、应用缓存、应用残留、聊天软件缓存、其他缓存、系统缓存）。
- **失败语义明确**：扫描失败、结果过期、无数据、无推荐项分别提示，"不会把空结果当成功"。首扫前"建议处理"显示「—」而不是 0。
- 已知缺口：Linux 宿主有分支但**未验收**。

三个插件对比着看，是三种责任分配：

| 维度 | c-cleanup | pancha | deepclean-mydisk |
| --- | --- | --- | --- |
| 谁做判断 | 规则库（+ 用户） | Agent 写语义，人做决定 | 规则 + 风险分档 + "问 AI" |
| 谁有执行权 | 用户确认后插件执行 | **只有用户** | 用户（两阶段） |
| 删除的默认形态 | 删除 / 迁移 | 移入废纸篓（可撤销批次） | 隔离/废纸篓 → 二次确认才永久删 |
| 失败姿态 | 不明即不删（fail-closed） | 只读扫描 + 不跟符号链接 | 不做扫描（无权限时） |
| 平台 | Windows | macOS 优先（有 Linux 分支？未声明） | macOS + Windows（Linux 未验收） |

### 4.4 `dsh-perf-boost`：一个诚实的性能插件长什么样

它的价值不在"优化了什么"，而在**它把每个开关的副作用列成了表**。这份表是整个"流畅度"话题里最稀缺的东西——绝大多数优化软件只报收益，不报代价：

| 开关 | 作用 | 可能会导致 |
| --- | --- | --- |
| 长对话省渲染 | `content-visibility: auto` 由一条 CSS 接管列表子项，占位高度取实测平均子项高度；末尾 4 项与 `aria-busy` 消息保持正常渲染，代码块按 300 px 跳过 | 快速滚动时被跳过的行可能空白一瞬 |
| 窗口隐藏不排帧 | 页面不可见时 `schedule()` 直接返回，`visibilitychange` 恢复 + 每秒看门狗兜底 | 后台标签页动画会停，切回补一帧 |
| 空闲降帧 | 20 秒无输入把 rAF 动画降到 30 fps | 长时间不动，动画看起来变慢 |
| 后台暂停定时器 | 不可见时跳过 `setInterval` 回调，不销毁也不重置周期，回前台各补跳一次 | 隐藏期间攒下的轮询只补一次，个别插件会看到一次跳变 |
| 大会话预热 | 启动 15 秒后把最近 10 个 8 MB 以上会话分段读进系统文件缓存，只读，跳过 10 分钟内改过的会话 | **读盘那几十秒里机械盘/低配机器打开会话可能反而慢一点，磁盘占用升高** |
| 关闭背景模糊 / 减少动画 | `backdrop-filter: none`；过渡时长置 0.001 ms | 观感改变 |

两个细节显示作者懂自己在做什么：

- "大会话预热"是**Host 侧**动作（要读会话文件），其它开关是 Client 侧。它自己也承认这条的代价可能是负收益（低配机器上预热期间更慢）——这是少见的"主动披露负收益"。
- 验证方式是**可观测断言**而非自夸：设置页显示"已生效：N 个列表，跳过 M 项渲染（共 K 项）"，控制台 `window.__dpbRaf` / `window.__dpbTimers` 为 `true` 表示接管成功；帧率角标只反映浏览器实际送帧数（上限等于显示器刷新率），**帧时/DOM 节点等细分数据请用 DevTools Performance**，插件不做常驻采样。

它的边界同样清晰：只改渲染进程，宿主代码不动、不写磁盘配置；不提供预设档位（因为"最优组合"取决于机器与会话规模，作者拒绝替你决定）；实测数据是单机（Windows 桌面端、200 Hz、缩放 100%），不能外推。

### 4.5 `dsh-perf-hud`：把"卡"变成可归因的证据

如果一个团队要长期维护"流畅度"，需要的不是优化开关，而是**观测**。`dsh-perf-hud` 是 DSH 生态里唯一按这个思路做的插件，它回答五个问题：

1. 现在顺不顺？→ FPS / 最差帧 / 帧内未归因，标题栏常显「流式 / 空闲 Ns」作为解读前提。
2. 卡的那一下是谁干的？→ Long Task 明细 + **四条腿归因**（组件名 / 包名 / DOM 写入者）。
3. 哪个插件在偷偷跑？→ 按插件的回调执行速率（/s）、峰值速率、同步耗时、DOM 写入次数与写入者。
4. 是插件的问题还是宿主/链路的问题？→ 宿主 event-loop p50/p99/max + 链路 RTT/吞吐，附阈值判色与"链路已排除"结论。
5. 关掉某个插件到底有没有用？→ 隔离实验：逐个关闭 60 秒，和**紧邻基线**对照，并给出**噪声底**。

第 5 条是本报告认为最有方法论价值的设计。它内置了"安慰剂控制"：不能只测"关掉后变快"，必须给出噪声底，否则任何差异都可能只是抖动。它还专门处理了"偶发卡顿"这个观测难题（守夜层）：每帧一条 12000 条环形缓冲（60 fps 下约 3.3 分钟）+ LoAF 观察器；一帧超过 100 ms 自动抓**前 10 秒 + 后 3 秒**原始切片；留存取三档并集（全局最差 10 次 + 每天最差 1 条 + 最近 3 次），并把"抓到但没留存"的次数单独记（`dropped`）与"没抓到"分开——这解决的是"只按全局最差排序会把昨天的卡整条挤掉"这个真实缺陷（README 记录：实测 `捕获 40 · 丢弃 38`）。

它的边界（README 有专门的"风险与边界（必读）"章节）：

- 它**不是** DevTools 的替代：DSH 自带开发者工具只采 Host CPU，Client 侧只有 Console 与只读 Sources，不给页面渲染 trace；所以事故包里 `devtools-trace` 缺失会**如实保留**，"不会因为装了它就变成已补上"。
- 它抓全量 Host fetch（含密钥）与"导出前减法脱敏"是两套口径——作者明确点出这个矛盾没有完全解决。
- 纯客户端意味着它观测不到 GPU 驱动、DPC/ISR、磁盘 IO 这些系统层指标。要那些，得用 PresentMon/LatencyMon/xperf 那一套（见 §9）。

### 5.2 功能分层：五层模型

把 30 余个项目按"它作用于系统的哪一层"分桶，比按平台或语言分更能看清架构差异：

```
第 1 层 分析（只读）：扫出空间去哪了，不做决定
    gdu / dua-cli / duf / squirreldisk / WinDirStat 类 / dsh-pancha 的扫描侧
        ↓ 需要"这是什么"的语义判断
第 2 层 清理（写，删除/移动）：按规则库判定可删性
    BleachBit / czkawka / MangoDisk / Mole / WindowsCleaner / deepclean-mydisk / c-cleanup
        ↓ 需要"该不该装/该不该留"的判断
第 3 层 配置（写，改行为）：注册表/组策略/服务/计划任务
    Win11Debloat / WinUtil / Sophia Script / privatezilla / Bloatynosy / RyTuneX / optimizer
        ↓ 需要"资源该给谁"的判断
第 4 层 调度（写，改优先级/内存策略）：进程优先级、内存清理、中断亲和、电源计划
    memreduct / WinMemoryCleaner / PC-Optimization-Hub / Process Lasso 类
        ↓ 需要"为什么慢"的证据
第 5 层 观测（只读，计量）：帧时、DPC、ETW、内存压力
    PresentMon / dsh-perf-hud / sidebar-perfmon / LatencyMon 类
```

一条经验法则：**层号越高的工具越应该"只读优先"**。第 1 层和第 5 层天然安全（不动状态），第 4 层最容易产生"看起来有效其实有害"的效果（清内存），第 3 层最容易产生"改完回不去"的效果（注册表/服务），第 2 层最容易产生"删了找不回"的效果。所以一个成熟方案的正确组合顺序是 **5 → 1 → 2 → 3 → 4**：先观测找到瓶颈，再分析空间，再清理，再改配置，最后才动调度。绝大多数"一键优化"软件从第 3、4 层开始动手，这是它效果不可验证的根源。

### 5.3 GitHub 头部项目深描（架构 / 功能 / 边界）

#### BleachBit —— 规则与引擎分离的教科书

- **架构**：Python 3 应用；清理能力来自**独立的 cleaner 定义**（XML 规则文件），引擎与规则解耦；GUI 与 CLI 双入口（`python3 bleachbit.py --help`）。GPLv3 **同时覆盖源码与 cleaner 定义**——这一点很关键：规则库是许可证的一部分，衍生规则也受约束。
- **功能**：释放磁盘空间 + 维护隐私（浏览器缓存、临时文件、应用痕迹）；有 Preview（先列出将要删除的文件）再 Delete 的两步交互。
- **边界**：跨平台（Linux/Windows）但规则库按应用版本维护，新版应用改了缓存路径就漏清；GPL 使其难以嵌入商业产品；无回滚机制（Preview 只是预演，不落盘台账）；不处理系统组件（WinSxS 类）。

#### czkawka / Krokiet —— Rust 重写 + 前端三拆

- **架构**：Rust core（README 强调"memory-safe Rust，几乎 100% 无 unsafe"）+ 多前端：`Krokiet`（Slint 框架，新一代默认 GUI）、`czkawka`（GTK4，**v12.0 是最后一个发布版**）、`Cedinia`（Android，Slint）、CLI（便于自动化）。核心算法靠多线程 + 高效算法 + **扫描缓存**（第二次扫描显著更快）。
- **功能**：重复文件、空文件夹、相似图片、大文件等"找出来"类；不是"清理"型而是"发现"型。
- **边界**：它不替你决定删什么（正确的边界）；相似图片判定有阈值，阈值错了就是误删；跨盘/跨符号链接的扫描语义需要用户理解；GTK 前端已停止演进，说明**同一项目多前端会自然收敛到一个**。

#### BCUninstaller —— 卸载器生态里的"事实标准"

- **架构**：C#/.NET（Apache-2.0）；不靠单一注册表项，而是**多来源发现已安装程序**（Store 应用、Steam、Windows 功能、NSIS/InnoSetup/Msiexec 等安装系统各有适配器），批量卸载 + 残留清理 + 孤儿程序检测。
- **功能**：批量卸载、按预设列表跑卸载器、清理 leftovers、检测 orphans。
- **边界**：残留判定必然有假阳性（删掉别的程序共享的运行时）；对 MSI 的自定义动作无能为力；README 顶部挂着"Looking for maintainers"——**这类工具一旦无人维护，就会在新 Windows 版本上悄悄失效**，这是开源清理工具最真实的生命周期风险。

#### Dism++ —— 规则文件开源、程序本体二进制的混合体

- **架构**：仓库 `Chuyu-Team/Dism-Multi-language` 承载的是**多语言资源 + `Data.xml` 规则文件**（README 原文："Data.xml — Dism++ rules file which provides cleanup and optimization rules"），以及崩溃统计与官网文档；程序本体以二进制发布（20716 stars、MIT、仓库主语言标记为 HTML，正说明它不是应用源码仓）。
- **功能**：基于 DISM 接口的组件存储清理与系统优化规则集，覆盖 WinSxS/更新残留/系统设置项。
- **边界**：**这是本报告里"能力最强、风险也最高"的一类**——它直接操作组件存储（WinSxS）。清理后系统可能无法卸载已安装更新、无法回滚；而且它的规则库不随用户环境自适应。仓库是资源仓这一点也意味着：**你能审计规则，但不能审计引擎**。

#### Win11Debloat —— 脚本形态的天花板

- **架构**：单文件 PowerShell，无需安装（`no installation required`），支持 CLI、**Windows 审核模式（Audit mode）**、对其他用户账户生效、配置导出/导入（同一套设置批量铺到多台机器）。
- **功能**：移除预装应用、关闭遥测、去掉侵入式界面元素。
- **边界**：脚本形态意味着**无 GUI 的事务感**（跑完才知道结果）、无回滚；系统大版本升级后部分项会被重置；需要相应权限；作为 61656 星的头部项目，它代表的是"脚本流"的极限，而不是"应用流"的上限。

#### WinUtil（Chris Titus Tech）—— 分发方式本身就是架构

- **架构**：PowerShell 工具集，执行方式是 `irm https://christitus.com/win | iex`（远程取脚本直接在内存执行），**必须管理员运行**（README 原文："WinUtil must be run as Administrator because it performs system-wide changes"）；提供 `-Preset Standard` 之类预设，把"选择"变成"配置项"。
- **功能**：安装（软件批量装）、tweaks 去臃肿、config 排障、Windows Update 配置。
- **边界**：`irm | iex` 是**最容易受供应链影响的分发方式**（每次执行都取最新内容，无版本钉死、无签名校验）；它对系统做的是"wide changes"，回滚要靠用户自己记得改了什么。

#### Sophia Script / Debloat-Windows-10 / Windows10Debloater —— 三种生命周期

- `farag2/Sophia-Script-for-Windows`：9859 stars，MIT，PowerShell，2026-11 仍在推送——**活跃**。
- `W4RH4WK/Debloat-Windows-10`：6130 stars，**已归档**（archived）。
- `Sycnex/Windows10Debloater`：18800 stars，**已归档**，最后一次推送 2023-03。
- `hellzerg/optimizer`：18220 stars，GPL-3.0，**已归档**（2026-01 后无推送）；接棒者是 `optimizerDuck`（10788 stars，C#）。

这四条放在一起是一个残酷的行业事实：**debloat 脚本的星数不随维护状态变化，但可用性随 Windows 版本变化**。一个 18800 星的归档脚本，在 Win11 24H2 上可能已经删不掉新加的预装应用。选型时必须看 `pushed_at` 与 `archived`，而不是 stars。

#### memreduct / WinMemoryCleaner —— "清内存"的物理真相

- `henrypp/memreduct`：C 写的原生应用（GPL-3.0），README 直说它"used undocumented internal system features (Native API) to clear system cache (**system working set, working set, standby page lists, modified page lists**) with variable result ~10-50%"；需要管理员权限。
- `IgorMundstein/WinMemoryCleaner`：C#，同样走"native Windows API"，便携、需管理员，README 给出 `choco install winmemorycleaner` 与 Scoop 装法（这是"其他渠道"的典型样本）。

这两个项目的功能描述本身就把边界写在脸上了：**"variable result ~10-50%"** ——清理效果因机器状态而异，且没有可预测性。从操作系统原理看（第 4 层工具的通病）：

- standby list 里装的是**可回收的文件缓存**，它存在的目的就是加速后续读盘。清掉它，任务管理器的"可用内存"数字立刻变好看，代价是**接下来所有读盘都要重新走物理 IO**。
- 工作集（working set）被强制 trim 后，进程要用页面时触发缺页，重新换入 —— 表现为"清完那一下后反而卡一阵"。
- 在物理内存充足的机器上，这个操作**净效果为负**；只有在"内存压力极大 + 无 SSD"的老机器上，才可能通过减少换页抖动获得边际收益。这不是观点，是缓存的基本物理：删掉有用的缓存不会让它更有用。

#### MangoDisk —— Tauri 2 + Rust core 的新一代形态

- **架构**：README 徽章明确 `Tauri 2` + `core-Rust`；一套代码覆盖 macOS / Windows / Linux；功能是"磁盘清理 + 存储分析 + 隐私保护"三合一。5269 stars、GPL-3.0，**仓库创建于 2026-08-01**（三个月做到 5000+ 星，说明这个赛道的需求与传播效率都很高）。
- **边界**：Tauri 意味着前端是 Web 技术栈、后端是 Rust，跨平台一致性好但对系统深层（驱动、WMI 级别）能力不如原生 C++；三平台共用一套规则库时，平台差异只能靠分支处理。

#### Mole（tw93）—— 73847 星的 macOS CLI 主力

- **架构**：Shell 实现的 CLI（GPL-3.0）+ macOS 应用外壳；功能面写得很清楚："Deep clean, uninstall, optimize, analyze disk and monitor your Mac"；仓库同时维护 `windows` 与 `linux` 分支（README 顶部有平台切换）。
- **边界**：CLI 形态对普通用户门槛高；Shell 实现意味着**跨平台要靠各自分支重写**，不是同一引擎；macOS 上受 SIP 与 TCC 约束（不能碰受保护路径）。

#### PowerToys（140535 stars）为什么不该算在内

它经常被列进"系统优化"清单，但 README 定位是 productivity 工具集（FancyZones / PowerToys Run 等）。本报告把它列出来**作为计数噪声的例子**：140535 星不等于"清理/加速"能力，星数是注意力指标，不是能力指标。

#### 观测类：PresentMon 与 PC-Optimization-Hub

- `GameTechDev/PresentMon`（Intel，MIT，2659 stars，C++）：**基于 ETW** 采集 CPU/GPU/Display 的帧时长与延迟，跨 DirectX/OpenGL/Vulkan、桌面与 UWP 应用；结构是 `PresentData/`（采集与分析库）+ `PresentMon/`（控制台应用，导出 CSV）+ `IntelPresentMon/`（GUI）。**这是"流畅度"话题里唯一有计量学地位的开源基础设施**——任何"变流畅了"的声称，理论上都该用它来证伪。
- `BoringBoredom/PC-Optimization-Hub`（1293 stars，无许可证）：不是工具，是**知识库**——收录输入延迟与刷新率优化的方法、论文与演示链接（如"12 ms 与 20 ms 的机器在瞄准任务完成时间上差 182 ms"）。它的价值是让"优化"这件事有可引用的证据基础。

### 5.5 Windows 专属机制解剖：五个被"一键工具"模糊掉的差别

这一节解释为什么"同是清理"，风险能差三个量级。下面五项机制，工具界面上往往只显示一个勾选框。

| 机制 | 实际在做什么 | 被模糊掉的边界 |
| --- | --- | --- |
| WinSxS / 组件存储 | 不是"缓存目录"，而是由**硬链接**组成的组件库：同一份文件被多个组件共享，删目录不等于删数据 | `StartComponentCleanup` 只删被取代的旧版本（保留最近一次）；加 `/ResetBase` 会连**卸载更新所需的备份**一起删——这两种语义在 UI 上常是同一个勾 |
| junction（目录联接） | 把一个目录路径重定向到另一个卷上的真实目录；本机 NTFS 有效，对旧程序兼容性最好 | 不能跨网络路径；对 OneDrive/加密/已挂载镜像无效；**删链接与删目标是两回事**，误删任一都会丢数据 |
| 符号链接 / 硬链接 | symlink 可指文件或目录（常需权限或开发者模式）；硬链接只能同卷、不能指目录 | 备份/同步工具对链接的处理不一致，可能把链接展开成实体或跳过 |
| 系统还原点 / 卷影副本（VSS） | 按块增量保存的历史快照，是"改坏了能回去"的唯一系统级退路 | 删掉即永失；把它当"磁盘垃圾"清掉的工具，等于**拆掉自己的安全网** |
| 存储感知（Storage Sense） | 不是清理器而是**策略引擎**：按阈值触发，包含"删除回收站里超过 N 天的文件""清理下载文件夹旧文件" | 这是唯一会**误删用户文件**的官方功能，必须显式配置，默认不应开启激进档 |

再补两条与"流畅度"直接相关、但常被忽略的机制差异：

- **TRIM 与碎片整理不是一回事**。`Optimize-Volume -ReTrim` 是告诉 SSD 哪些块已无效、可以回收；对闪存做"全盘碎片整理"无收益且增加写入磨损（传统 defrag 只对机械盘有意义）。
- **"内存"在 Windows 里至少是四个量**：工作集（working set，进程已映射的物理页）、提交量（commit，含页面文件承诺）、standby list（可回收的文件缓存）、modified page list（待写回）。`memreduct` 的 README 明确写它清的是 **system working set / working set / standby page lists / modified page lists** 这四类——知道它清的是缓存而不是"垃圾"，才能判断何时不该用它。

### 5.6 GitHub 上的 DSH 侧：索引不是全集

## 6. 横切架构对比：同是"清理/加速"，信任模型差三个量级

把 DSH 插件与 GitHub 项目放到同一张表里比，看的不是功能，是**它们各自能碰到什么、出错时谁承担**。

| 维度 | DSH 插件（Host 半） | DSH 插件（Client 半） | 便携原生应用（memreduct / WinMemoryCleaner / MangoDisk） | 管理员脚本（WinUtil / Win11Debloat） | 系统集成应用（Dism++ / optimizer） |
| --- | --- | --- | --- | --- | --- |
| 运行位置 | 宿主 Node 进程内 | 浏览器渲染进程 | 独立进程 | PowerShell 进程 | 独立进程 + 服务/驱动 |
| 权限基线 | 与用户同级（可自查提权） | 无系统权限 | 用户级，多数操作需管理员 | 必须管理员 | 管理员 |
| 数据来源 | 文件系统 + 子进程 + 宿主 registry | DOM / 性能 API | Win32/Native API、文件遍历 | 注册表 / 服务 / 包管理 | DISM、注册表、服务 |
| 执行引擎 | TypeScript/JS + 外部命令 | 前端事件循环 | 各语言（C/C#/Rust） | PowerShell 语句 | 原生 API + 规则 XML |
| 回滚能力 | 视插件（账本/隔离区/快照） | 不适用 | 通常无 | 通常无（靠导出配置） | 部分（依赖系统还原点） |
| 卸载干净度 | 有 `dsh-unplug`/`update-center` 等专治残留 | 删包即净 | 便携版删目录即净 | 不落地 | 落地即留痕 |
| 主要风险 | 供应链 + 宿主同权 | 无 | 提权 + 注册表写入 | 一次性大范围改动、无版本钉死 | 系统组件不可逆 |

三条由此得出的工程结论：

1. **"插件"不等于"低风险"**。Host 半插件与宿主同权，它想删什么就删什么；Client 半插件反而天然安全（碰不到文件系统）。所以评估 DSH 清理类插件，第一件事是分清它是哪一半——`dsh-perf-boost` 写"全部改动只发生在渲染进程"是在主动划定这个边界，`dsh-pancha` 写"这是软约束"是在承认自己没划死。
2. **回滚能力是分水岭**。表里"回滚能力"一列，凡是"无"的行，其风险都由用户承担；凡是"账本/隔离区/快照"的行，风险由插件作者承担一部分（他要写对台账）。这也解释了为什么新一代清理工具都长成"扫描→分级→预览→两阶段→台账"的形状：**回滚是唯一能把"不可逆"变成"可逆"的机制**。
3. **分发方式决定供应链风险**。`irm | iex`（每次取最新）> `github:owner/repo`（取最新提交 + 现场构建）> npm 带预构建（可钉版本 `@1.0.5`）> 便携二进制约等于固定版本。DSH 生态里 `dsh-windows-c-cleanup` 明确建议"日常使用走 npm，最省心"，并提示 git 装法会触发构建审批——这是把供应链权衡写进文档的正确做法。

### 6.1 其他渠道：这些工具实际上从哪来

"借另外渠道的开源"这句要求，落地就是五个分发面的差异：

| 渠道 | 代表样本（已验证） | 特点 | 边界 |
| --- | --- | --- | --- |
| npm | `dsh-plugin-catalog`、`dsh-windows-c-cleanup`、`deepclean-mydisk`、`dsh-perf-hud`、`dsh-workspace-cleaner` | 预构建、可钉版本、DSH 插件的主分发通道 | 无签名/无审计；`prepare` 脚本可执行任意代码 |
| Chocolatey | `choco install winmemorycleaner`（README 明示） | Windows 包管理，校验哈希 | 社区维护包，版本可能滞后 |
| Scoop | `scoop install extras/winmemorycleaner`（README 明示） | 免提权装到用户目录、便携、易回滚 | extras bucket 质量参差 |
| winget | 大量清理工具已进官方源 | 微软签名体系、可审计来源 | 上架门槛使小众项目缺席 |
| Homebrew / AUR / 各发行版仓库 | Mole、BleachBit、Stacer 等 | 源码构建 + 打包者背书 | AUR 无审核；打包者≠作者 |

一条实用建议：**能走包管理器就别走 `irm | iex`**。包管理器至少给你"来源可查、版本可钉、卸载可逆"三件事，而 `irm | iex` 三件都没有。

### 6.3 回滚机制的四种实现，与它们各自的失效点

"可回滚"是所有新式清理工具的核心卖点，但四种实现方式的强度差很多，失效点也各不相同：

| 实现 | 机制 | 强度 | 典型失效点 |
| --- | --- | --- | --- |
| 移到废纸篓/隔离区 | 文件仍在同一卷上，只是换了目录 | 中（可撤销，但**不释放空间**） | 跨卷移动变成"复制+删"，失败会留下半截；macOS 拒写废纸篓时需退到自有 trash 目录 |
| 台账 + 反向操作 | 记录每步动作，撤销时逐步反向执行 | 中高（可精确撤销） | 若应用在迁移后往旧路径写了新数据，反向操作会把新数据搬回去，造成错位 |
| 快照（插件/配置） | 操作前存一份配置或目录快照 | 高（整包回退） | 快照范围不包含"运行时产生的数据目录"时，回滚后仍不一致（`dsh-plugin-update-center` 用 snapshots/rollback 处理插件更新，这类边界要靠作者自己划） |
| 系统还原点 / VSS | 块级历史快照 | 最高（系统级） | 需要用户**预先**建点；回滚会连带撤销此期间的其他改动 |

一条通用规律：**回滚能力取决于"有没有记录原始状态"，而不取决于"有没有撤销按钮"**。没有台账、没有快照、没有还原点，所谓"一键还原"只能是谎言。这也是为什么 §7.4 的 12 条清单里，"落台账"与"只做移动"占了两位。

## 7. 边界专章（一）：DSH 插件生态的结构性限制

### 7.1 软约束 vs 硬约束，是整个生态最重要的一条线

`dsh-pancha` 自己写下的那句话值得再引一次：约束来自提示词，"这是软约束——默认会话本身仍有文件/命令工具；要工具级隔离，需要自己加一个受控 preset"。

把这句话展开，就是 DSH 生态的四级隔离梯度：

| 级别 | 机制 | 强度 | 样本 |
| --- | --- | --- | --- |
| L0 | 提示词约束（"只分析不执行"） | 最弱，可被模型忽略或注入绕过 | pancha 的默认形态 |
| L1 | 工具面裁剪（不给文件/命令工具） | 中，模型想做也做不到 | 需要自定义 preset |
| L2 | 执行环境隔离（Sandboxie 写时复制盒） | 强，写入落在副本 | `dsh-sandboxie-redirect` |
| L3 | 独立低权账户 / 容器 / 只读挂载 | 最强 | 需自建 |

绝大多数"Agent 清理磁盘"的方案停在 L0 或 L1。这不是偷懒，是因为 L2/L3 会牺牲可用性（沙箱里跑不了需要提权的清理）。**但用户必须知道自己在哪一级**——把 L0 当 L3 用，是这类工具最典型的误用。

### 7.2 供应链：8655 个插件，没有一个经过审计

事实层面：插件目录索引里 4481 条记录全部带 `versions` 字段，即都能以 npm 包形式安装；git 装法会跑 `prepare` 构建脚本；没有任何机制对插件代码做签名或审计（索引里也没有 `signature`/`attestation` 类字段）。推论：

- 装一个插件 = 信任一个陌生作者的代码在你的机器上以你的权限运行，且它能再调 `PowerShell` 提权。
- 清理类插件的攻击面比 UI 类更大：它天然需要文件删除权限，恶意版本可以在"扫描"阶段就把保护名单里的路径加进去。
- 缓解手段只有工程纪律：优先 npm 钉版本 → 装前看 `repository` 与 README 的安全章节（`deepclean-mydisk` 有 `SECURITY.md` 与私下报漏洞流程，这是正向信号）→ 用 `dsh-unplug`/`dsh-plugin-diraud` 保持插件面最小 → 对碰系统目录的插件单独开 profile。

### 7.3 版本耦合：插件与宿主是硬绑定

`dsh-pancha` 标注"前置 dsh 0.2.x，在 0.2.1-rc.1 上验证"；`dsh-perf-hud` 徽章写 `DSH 0.2.1-rc.1`；`dsh-workspace-cleaner` 要 Node ≥ 22；`dsh-wallpaper-engine` 甚至要求 `dsh-better-sidebar ≥ 0.19.0`。这类"宿主 API 变动即插件失效"的耦合，是插件生态的结构性成本：**升级 DSH 之前要先确认清理插件还能用，否则可能装上一个跑不起来的清理工具还以为自己清过了**。

### 7.4 Agent 清理的 12 条安全设计清单

从三个 DSH 清理插件的实践里能提炼出一套可复用的设计规则。这份清单的用途是**自己写插件时照着做**，或**评估别人的插件时逐条对照**；每条都标注了出处，不是我编的原则：

| # | 规则 | 出处 |
| --- | --- | --- |
| 1 | 扫描阶段只读，且**不跟随符号链接** | pancha（`readdir`/`stat`，不跟随符号链接） |
| 2 | 保护名单是硬约束：**未收录规则的一律按保护处理**，且优先级高于用户自定义规则 | c-cleanup（"不明即不删"，用户规则也不得覆盖） |
| 3 | 删除前必须能报出**真实大小**与重建代价 | c-cleanup（先量后删） |
| 4 | 分级不少于四档，每档带**判定理由**而不是只给颜色 | c-cleanup 五级 / deepclean 四档 |
| 5 | 执行只做"移动"，**永久删除单独一步、二次确认** | deepclean（隔离区/废纸篓 → 确认才永久删）、pancha（只有废纸篓） |
| 6 | 每批操作落**本地台账**，支持整批撤销 | pancha（`ledger.json` + 撤销这批）、c-cleanup（迁移台账） |
| 7 | Agent **只写语义与标记，不持有执行权** | pancha（"它没有执行权，只能写标记"） |
| 8 | 提供**异议通道**：Agent 可对不同意的决定写 objection，但不能改决定 | pancha（`disk_canvas_object`） |
| 9 | 权限不足时**不做部分扫描**，直接拒绝并说明 | deepclean（macOS 未授「完全磁盘访问」时不扫描） |
| 10 | **空结果 ≠ 成功**：无数据/结果过期/扫描失败/无推荐项分别提示 | deepclean（"不会把空结果当成功"） |
| 11 | **迁移优先于删除**，迁移必须可回滚 | c-cleanup（junction + 台账） |
| 12 | 平台能力差异**显式声明**（哪个平台验收过、哪个没验收） | deepclean（Linux 未验收）、pancha（版本兼容表） |

注意这 12 条里有 **7 条（2/3/4/5/7/8/11）与"删除"本身无关**，全部是"如何让人做出正确决定"或"如何让决定可撤回"。这是一个值得记住的比例：清理工具的主体工作不是删文件，是**组织判断与保留退路**。删文件那一步，`unlink` 一行就够。

反过来说，只要一个插件在这 12 条上缺 3 条以上，它就不该被允许碰系统盘——不是因为作者水平差，而是因为**缺的每一条都对应一类曾经发生过的事故**。

## 8. 边界专章（二）：物理、不可逆、平台、许可

### 8.1 物理边界：有些"优化"在原理上无效

- **清内存**：standby list 是可回收缓存，清掉只会让后续读盘更慢（§5.3）。在内存充足的机器上是负收益。
- **"释放内存能加速"**：只有在内存压力导致持续换页时成立；判断依据是硬缺页率与页面文件活动，不是"可用内存"数字。
- **清理大文件能提速度**：错误。空间与速度无因果关系，除非磁盘使用率超过阈值导致碎片/预留不足。清理解决的是"装不下"，不是"跑不快"。
- **注册表清理能提速度**：无可靠证据支持；注册表查询是内存哈希查找，与项数弱相关。
- **预读/预热**：`dsh-perf-boost` 的大会话预热自己就承认可能反而更慢（机械盘/低配）——**任何缓存策略都是双刃**。

### 8.2 不可逆边界：三个必须知道的坑

1. **WinSxS / 组件存储**：`DISM /StartComponentCleanup /ResetBase` 之后无法卸载已安装更新。`c-cleanup` 把 WinSxS 放进"🟡 谨慎删除（需管理员）"是对的。
2. **系统还原点 / 卷影副本**：删掉后无法回滚到之前的系统状态——而它恰恰是前面所有"改配置类"操作的唯一退路。清理工具若把还原点列为可删项，等于**拆掉自己的安全网**。
3. **休眠文件 / 页面文件**：删掉会失去休眠、影响崩溃转储与内存换页；某些"极致瘦身"教程会把它们删掉，代价是系统稳定性。

### 8.3 平台边界

- **Windows**：UAC 决定能不能碰系统目录；驱动/服务级操作会与安全软件、反作弊系统冲突（这是"优化软件导致游戏封号/蓝屏"的真实来源）；不同大版本（Win10 19045 vs Win11 24H2）预装项与路径不同，脚本易失效。
- **macOS**：SIP 限制系统目录；TCC 的「完全磁盘访问」是硬门槛（`deepclean-mydisk` 未授权就不扫描）；废纸篓与源在同一卷时**移入废纸篓不释放空间**。
- **Linux**：无注册表概念，清理对象是包缓存/日志/容器层；`fstrim` 对 SSD 是常规维护；Stacer 这类 GUI 工具已停更（README 明示 abandoned），现代做法是用 CLI 组合（见 §10）。

### 8.4 许可与合规边界

- **GPL-3.0**（BleachBit、czkawka、Mole、Stacer、memreduct、WinMemoryCleaner、MangoDisk、optimizer、RyTuneX-AGPL）：衍生分发需开源；BleachBit 的规则文件也在 GPL 内。
- **MIT / Apache-2.0**（Win11Debloat、WinUtil、Sophia、BCUninstaller、PresentMon、WinMemoryCleaner 徽章声明、DeepSeek 生态多数插件）：商用友好。
- **无许可证**（`PC-Optimization-Hub`、`optimizerDuck` 标 NOASSERTION）：默认保留所有权利，**企业环境不应直接采用**。
- **企业合规**：debloat 类脚本会改动遥测/更新策略，可能与组织 IT 策略冲突；清理工具删除审计日志可能违反留痕要求。

### 8.5 反模式清单：15 种常见"优化"为什么无效或有害

这一节把前面散落的原理集中成一张负面清单。每条给"做法 → 为什么 → 正确做法"。

| # | 常见做法 | 为什么无效或有害 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 定时清 standby list 当"加速" | 清掉的是可回收文件缓存，后续读盘全部落回物理 IO | 只在硬缺页率高、内存压力确证时手动清一次 |
| 2 | 关闭 SysMain/Superfetch | 它做的就是预读；关掉后冷启动与常用程序启动变慢 | 保留；若在纯 SSD 且内存充足，收益本就很小 |
| 3 | 删 `hiberfil.sys` | 失去休眠；快速启动（若启用）一并失效 | 真要省空间用 `powercfg /h /type reduced` |
| 4 | 关闭或极大缩小页面文件 | 内存吃紧时直接触发提交失败/程序崩溃；崩溃转储也丢失 | 保持系统托管，或固定为物理内存的合理比例 |
| 5 | 关闭系统还原点/删卷影副本 | 拆掉改配置类操作唯一的回滚退路 | 保留一个小的还原点配额，改配置前手动建点 |
| 6 | 注册表清理 | 收益无可测证据；误删导致应用异常且难以定位 | 不清理；卸载残留用专用卸载器处理 |
| 7 | 关闭 Windows Search 索引 | 搜索变慢，收益只在极端 IO 瓶颈机上可见 | 收窄索引范围而不是关闭服务 |
| 8 | 常驻"内存优化"托盘程序 | 自身占内存并周期性制造 IO，长期看是净成本 | 用系统自带的任务管理器观察，按需手动 |
| 9 | 批量把服务启动类型改为禁用 | 破坏更新、打印、蓝牙、音频等依赖链，故障难回溯 | 只改有明确证据的单项，并记录原值 |
| 10 | 对 SSD 做"全盘碎片整理" | 对闪存无收益且增加写入磨损 | 用 `Optimize-Volume -ReTrim`（TRIM），不要 defrag |
| 11 | 关闭/延迟系统更新当"优化" | 把性能问题换成安全问题；大版本落后会失去驱动支持 | 保留更新，用活动时间控制重启窗口 |
| 12 | 追求"开机 3 秒"，禁用全部自启 | 自启项里常含输入法、同步、驱动面板，禁完体验更差 | 只看"启动影响:高"的项，逐项判断 |
| 13 | 装带内核驱动/hook 的"加速球" | 内核态代码与安全软件、反作弊直接冲突，蓝屏与封号风险 | 不碰内核态；一切用户态可完成 |
| 14 | `DISM /ResetBase` 深度瘦身 WinSxS | 之后无法卸载已安装更新、无法回滚组件 | 只跑 `StartComponentCleanup`，不加 `/ResetBase` |
| 15 | 把"CPU 占用 0%"当健康标准 | 后台索引/更新/预读是正常工作，压到 0 反而变慢 | 看"是否在等待"而不是"是否在忙" |

如果只能记一条，记这条：**清单里 12 条的共同错误是把"指标好看"当成"系统变好"**。可用内存、CPU 占用、启动秒数都是**容易观测但不等价于目标**的代理指标；真正的目标是"我要做的事多快完成、卡不卡"。代理指标一旦被当成目标，优化就会自然走向自欺。

### 8.6 动手前的八问：任何清理工具都适用的快速核查

不需要读完全部文档，回答这八问就能挡掉绝大多数事故：

1. **它删还是会移？** 会移就有退路；"直接删"必须能列出它将删的具体路径。
2. **它有没有"预览"？** 预览是把不可逆变成可审视的最小代价。没有预览的工具直接放弃。
3. **它的规则库谁维护、多久改一次？** 规则不更新的清理工具，在新版应用上要么漏清要么误删。
4. **它要我提权吗？为什么需要？** 用户目录内的缓存清理**不应该**需要管理员权限；要求提权却说不清用途的，一律不装。
5. **它会写注册表/服务/计划任务吗？** 写就要问：原值记在哪、怎么恢复。只写用户态配置的工具风险低一个量级。
6. **它碰不碰还原点、页面文件、休眠文件、WinSxS？** 这四项属于"清理收益低、不可逆代价高"的类别，默认应拒绝。
7. **它把数据发到哪？** 无遥测、账本只落本机，是可信信号；要求登录账号或上传目录清单的，先在隔离环境跑。
8. **它出错时会告诉我吗？** 空结果当成功、失败静默跳过的工具，比报错的工具危险得多。

这八问里没有一条问"能清多少 GB"——因为**能清多少是结果，能不能后悔是前提**。顺序颠倒过来，就是各种"清理完系统坏了"的起点。

## 9. 怎么自证"确实变流畅了"：一套可执行的度量方法

绝大多数"优化"讨论失败在没法证伪。可行的最小方法：

1. **定指标**：交互场景用帧时 p50/p99 与最差帧（不是平均 FPS）；打开文件场景用首次字节时间；系统层用 DPC/ISR 延迟与硬缺页率。
2. **定对照组**：同机、同会话规模、同负载；A/B 交替各 3 次以上；记录**噪声底**（同一配置重复测量的波动幅度）。`dsh-perf-hud` 的隔离实验就是这个思路的现成实现（关插件 60 秒 + 紧邻基线 + 噪声底）。
3. **用有计量学地位的工具**：交互/游戏 → `PresentMon`（ETW，帧时长与延迟）；前端 → Chrome DevTools Performance + LoAF；系统 → ETW/xperf、性能计数器。
4. **排除安慰剂**：如果差异小于噪声底，就是没有差异。这条纪律能过滤掉 80% 的"优化玄学"。
5. **记录副作用**：每个开关的"可能会导致"（`dsh-perf-boost` 的表就是模板）必须一起记，否则你只证明了收益、没证明代价。

---

### 9.1 一份可照抄的实验样板

想说服自己（或别人）某个改动有效，最少需要这些步骤：

1. **写清假设**："装 X 之后，DSH 长会话滚动的最差帧从 A 改善到 B"。假设里必须出现指标名与方向。
2. **固定环境**：同机、同电源计划、插电、无后台更新、同会话文件、同视口尺寸。环境变量没固定，后面全是噪声。
3. **交替 A/B**：A（关）→ B（开）→ A → B …… 各至少 3 次，**不要"先跑 3 次 A 再跑 3 次 B"**（会引入时间趋势，例如缓存越跑越热、系统越跑越闲）。
4. **算噪声底**：同一配置重复测量的极差（max−min）就是噪声底。差异小于噪声底 = 没有差异。
5. **看分布不看均值**：帧时看 p50/p99 与最差帧；均值会被一次卡顿掩盖，而用户感知的恰恰是那次卡顿。
6. **记录副作用**：内存占用、磁盘 IO、观感变化（例如内容跳位、图片白一下）一并记录。
7. **留下可复现材料**：截图、导出 CSV、插件版本号、会话文件大小。

两个真实误判模式，几乎人人会踩：

- **冷启动偏差**：第一次运行因为要读盘/建索引一定更慢。把"第一次"当基线，会让任何改动都看起来有效。正确做法：每组都预热一次再计时。
- **后台干扰**：Windows Update、安全软件全盘扫描、云盘同步都可能在你的测量窗口里跑。判断方法：同时记录磁盘队列长度，若测量期间出现尖峰，整组数据作废重测。

## 10. 选型矩阵与最小方案

### 10.1 按场景选

| 场景 | 推荐组合 | 理由 |
| --- | --- | --- |
| 只想让 DSH 界面顺一点 | `dsh-perf-boost` + `dsh-perf-hud` | 一个做让路、一个做观测；两者都在渲染层，风险最低 |
| DSH 目录占了几十 GB | `dsh-workspace-cleaner` / `dsh-brutal-delete`（谨慎） + `dsh-plugin-update-center` | 先回收会话与插件残留，再考虑系统盘 |
| Windows C 盘爆满 | `dsh-windows-c-cleanup`（分级+迁移） 或 `deepclean-mydisk`（两阶段） | 都要"先量后删 + 可回滚" |
| 需要审计的磁盘决策 | `dsh-pancha` | Agent 只写语义、人做决定、只移废纸篓 |
| 跨平台一次性清理 | MangoDisk（Tauri/Rust） 或 Mole（macOS CLI） | 同一引擎多平台；Mole 需 CLI 习惯 |
| 找空间去哪了 | `gdu` / `dua-cli` / `duf`（CLI）或 squirreldisk（GUI） | 只读、快、可脚本化 |
| 卸载干净 | BCUninstaller（需注意维护状态） | 多来源发现 + 残留清理 |
| 老机器内存吃紧 | `memreduct` / WinMemoryCleaner（谨慎） | 仅在内存压力确证时用，且知道代价 |
| 实测帧率/延迟 | PresentMon | 唯一有计量学地位的开源工具 |
| 企业批量铺配置 | Win11Debloat（导出/导入 + Audit 模式） | 可复现、可批量；注意归档项目的时效 |

### 10.2 零依赖最小方案（不装任何第三方）

```
Windows：
  1) 观测：任务管理器 → 性能；资源监视器（磁盘队列/硬缺页）；perfmon /rel
  2) 空间：设置 → 存储 → 存储感知（自动清理临时文件/回收站）
  3) 组件：Dism /Online /Cleanup-Image /AnalyzeComponentStore
           Dism /Online /Cleanup-Image /StartComponentCleanup   （不加 /ResetBase 以保留卸载更新能力）
  4) 磁盘：Optimize-Volume -DriveLetter C -ReTrim（SSD）或 -Defrag（HDD）
  5) 启动项：任务管理器 → 启动；Get-CimInstance Win32_StartupCommand
  6) 电源/调度：powercfg /energy、powercfg /batteryreport
macOS：
  df -h / du -xh -d1 ~ | sort -rh | head；tmutil listlocalsnapshots / tmutil deletelocalsnapshots
Linux：
  du -xh --max-depth=1 / | sort -rh；journalctl --vacuum-size=200M；docker system prune
  fstrim -av；apt clean / dnf clean all / pacman -Sc
```

这套组合覆盖了"清理 + 观测"里 80% 的真实需求，且全部可回滚、无供应链风险。第三方工具的增量价值主要在**分级判断**与**可回滚的多步操作**上——如果你能接受"多花十分钟看清楚"，内置命令通常够用。

### 10.3 个案复盘：一台只剩 3 GB 的开发机

把前面的工具串成一条真实可执行的链路。假设 Windows 开发机 C 盘告急，目标是"腾出 30 GB 且不破坏环境"。

**第 0 步：先设回滚点**（这一步最容易被跳过，也最贵）。建一个系统还原点，或至少记录将要改动的服务的原始启动类型。

**第 1 步：观测，别急着手**。资源监视器看磁盘队列与硬缺页；`设置 → 存储` 看分类占用；若装了 `dsh-perf-hud` 之类的观测插件，先确认"卡"是磁盘 IO 还是渲染。此时不做任何删除。

**第 2 步：分析到目录级**。用只读工具定位：`gdu -d 2 C:\Users\<me>` 或图形化树图。产出是一张"大目录 + 大小"的清单，这张清单就是后面所有决策的依据。

**第 3 步：按五级判定每一项**（照 c-cleanup 的分级模型手工做一遍）：

| 典型目标 | 分级 | 动作 |
| --- | --- | --- |
| 包管理器缓存（npm/pnpm/pip/cargo） | 🟠 建议迁移 | 改镜像与 store 路径到 D 盘，用 junction 指向 |
| IDE 索引（`.idea`/`.vscode`/JetBrains caches） | 🟡 谨慎 | 可删但重建数小时；优先迁移配置目录 |
| 端侧 AI 模型缓存（几 GB 起） | 🟠 建议迁移 | 改环境变量指到 D 盘，应用无感 |
| WSL / Docker 虚拟磁盘（`ext4.vhdx`） | 🔴 保护（本体）/ 🟠 迁移 | 先 `wsl --shutdown` 再 `Optimize-VHD` 压缩；整体可迁到 D 盘 |
| 浏览器缓存、临时文件、升级残留 | 🟢 安全 | 批量删 |
| 用户文档、凭据、聊天记录 | 🔴 永不自动删 | 只提示，不动作 |

**第 4 步：迁移优先**。当 C 盘的问题是"放错了地方"时，迁移的收益是长期的（不再回涨），而删除的收益是一次性的。这一步做完，往往已经腾出大部分空间。

**第 5 步：组件存储瘦身（可选，谨慎）**。先 `Dism /Online /Cleanup-Image /AnalyzeComponentStore` 看能回收多少，再决定是否 `StartComponentCleanup`；**不加 `/ResetBase`**，否则失去卸载更新的能力。

**第 6 步：长期防护**。打开存储感知、把虚拟磁盘与缓存路径固化到 D 盘、把"每月清一次"改成"每季核一次"。

这条链路与"一键优化"的差别不在步骤多少，而在**第 0 步与第 3 步**：一键工具没有回滚点，也没有分级——它把判断权收走了，而这恰恰是清理里唯一不能外包的部分。

## 11. 趋势判断（基于本次采样的可观察证据）

1. **"可审计流水线"正在取代"一键清理"**。DSH 侧三个清理插件全部是"扫描→分级→预览→执行→台账"，GitHub 侧新项目（MangoDisk 2026-08 建仓、MacSift 2026-04、PureMac 2026-04）也都把"可撤销"写进第一屏。反例是老一代的 `optimizer`（已归档）与各类一键脚本。
2. **Rust + Tauri/Slint 成为跨平台清理工具的主流技术选型**：czkawka/Krokiet（Rust+Slint）、MangoDisk（Rust+Tauri 2）、squirreldisk（Rust）、RyTuneX（C# 但 AGPL）、windows-disk-cleaner-skill（Rust）。动机是"内存安全 + 单二进制 + 跨平台 GUI"三合一。
3. **Agent 化清理出现了新品类，但都停在"建议权"**：`std-microblock/windows-disk-cleaner-skill`（88 stars，Rust，Apache-2.0，2026-09 建仓）、`vudsen/ai-disk-cleaner`（340 stars，Go）、DSH 侧的 pancha/deepclean/c-cleanup。它们的共同形状是 **Agent 产生语义与建议，人保留执行权**——这不是技术限制，是责任归属的必然。
4. **debloat 赛道进入平台期，且维护状态分化明显**：三个头部脚本已归档（Windows10Debloater 18800、Debloat-Windows-10 6130、optimizer 18220），活跃的是 Win11Debloat（61656）与 Sophia Script（9859）。星数与维护状态脱钩，选型必须看 `pushed_at`。
5. **"性能"这个词正在从"系统"迁移到"应用"**。DSH 侧 6 个所谓性能插件里，4 个优化的是应用自身（渲染、token、网络），只有观测类的 2 个触及系统指标。这个重心迁移在 GitHub 侧也成立：`topic:system-optimization` 只有 538 个仓库且头部是磁盘工具，而前端/游戏延迟优化（PC-Optimization-Hub 类）反而是知识密度最高的部分。

## 12. 维护性评估：这个清理工具明年还能用吗

清理/优化工具的失效方式很隐蔽：它不会报错，只会**静默地少清一点**——因为新版本应用把缓存换了路径、Windows 改了预装清单、注册表键挪了位置。所以选型时应把"维护状态"当作第一筛选条件，而不是 stars。

四个可核查的判据，按有效性排序：

1. **`archived` 标记与 `pushed_at`**：归档 = 明确停止维护。本次采样里 3 个头部项目已归档（`Sycnex/Windows10Debloater` 18800 stars、`W4RH4WK/Debloat-Windows-10` 6130 stars、`hellzerg/optimizer` 18220 stars），另有一个 README 直接写"This project has been abandoned"（`oguzhaninan/Stacer`）。**星数不随维护状态下降**，这是最容易骗人的指标。
2. **规则库/清单的更新频率**：清理工具的实质资产是规则，不是代码。看最近几次提交是在改规则还是改 README——只改文档的项目，实际上已经停了。
3. **issue 响应**：搜"没有清理""已失效"类 issue 是否有维护者回复。无人响应的失效报告是最真实的可用性信号。
4. **bus factor**：单人维护的项目（README 里挂 "Looking for maintainers"，如 `BCUninstaller`）随时可能停摆；单人 + 无 CI + 无测试的项目风险加倍。

对照样本（本次采样）：**活跃且持续推送**——`Raphire/Win11Debloat`（61656）、`farag2/Sophia-Script`（9859）、`qarmin/czkawka`（34827）、`tw93/Mole`（73847）、`harry0703/MangoDisk`（5269，2026-08 建仓）；**停滞或归档**——`privatezilla`（2023-04 后无推送）、`Windows10Debloater`、`Debloat-Windows-10`、`optimizer`、`Stacer`。

一条可直接执行的纪律：**在 stars 排序之后，按 `pushed_at` 降序再排一次**。两次排序结果差得越多，说明这个赛道"注意力"与"可用性"脱钩越严重。
